02

Timer Foundation

Timer tạo tick đều để các sự kiện phần cứng có mốc thời gian.

f_TIM172 MHzClock đến timer.
PSC = 71f_CNT = 1 MHzCounter tăng một triệu lần/giây.
T_tick1 usMỗi counter tick mất một micro giây.

ARR là giới hạn đếm

Với `ARR = 99`, counter đếm từ `0..99`: tổng cộng `100` tick. Khi đạt ARR, timer update/overflow rồi bắt đầu vòng mới từ `0`.

T_PWM = (ARR + 1) × T_tick = 100 × 1 us = 100 us
CheckpointARR không phải đơn vị thời gian. Nó cần kết hợp với `T_tick` để tạo ra thời gian.
03

PWM Output

ARR tạo khung thời gian; CCR1/Pulse quyết định mức HIGH trong khung đó.

Chu kỳ100 us(ARR + 1) × T_tick
Tần số10 kHz1 / T_PWM
DutyCCR1 / 100Với ARR = 99.

CCR1 / Pulse làm gì?

Với `T_tick = 1 us`, `CCR1 = 50` làm tín hiệu PA8 HIGH khoảng `50 us` trong chu kỳ `100 us`, tương đương duty gần `50%`. `Pulse` là tên CubeMX/HAL cho giá trị compare nạp vào CCR1.

CCR1/PulseHIGHDuty gần đúngÝ nghĩa

7575 us75%Mức cao
99gần 100 usgần 99%Mức tối đa theo mapping
Checkpoint10,000 là số chu kỳ PWM mỗi giây; 100 là số counter tick trong một chu kỳ.
04

Throttle ADC

Chiết áp tạo điện áp, ADC biến điện áp thành số, code map số đó sang Pulse.

Chiết áp 3 chân

  • Một chân ngoài → `3.3V`
  • Chân ngoài còn lại → `GND`
  • Chân giữa → `PA0 / ADC1_IN0`

Không đưa 5 V vào chân ADC Blue Pill.

ADC 12-bit

0 V0Ga thấp
1.65 V≈2048Ga giữa
3.3 V≈4095Ga cao

Mapping cùng chiều

Pulse = ADC_value × 99 / 4095

Ví dụ: `ADC = 2048` → `Pulse ≈ 50` → duty gần `50%`. ADC nhỏ không tự làm CCR1 nhỏ; chính code mapping tạo ra quan hệ đó.

Firmware`adc_reader` chỉ trả raw `0..4095`; `app_motor_control` mới làm mapping.

06

HAL Modules

Mỗi module có một trách nhiệm; `main.c` chỉ khởi động và gọi app update.

ModulePublic responsibilityHardware
adc_reader.h/.cĐọc raw ADC và trả `0..4095`.PA0 / ADC1_IN0
motor_pwm.h/.cStart PWM, clamp và ghi Pulse/CCR1 `0..99`.PA8 / TIM1_CH1
motor_driver.h/.cChọn Forward, Reverse, Stop, Brake.PB12 / PB13
app_motor_control.h/.cNối ADC → mapping → PWM.hadc1 / htim1

HAL flow

  1. CubeMX cấu hình peripheral.
  2. `MX_..._Init()` khởi tạo.
  3. Gọi start cho peripheral cần chạy.
  4. Đọc ADC và map giá trị.
  5. Ghi Pulse vào CCR1.

`main.c` giữ mỏng

Include module trong `USER CODE BEGIN Includes`. Gọi start/init trong `USER CODE BEGIN 2`. Trong vòng lặp, gọi `app_motor_control_update(&hadc1, &htim1)` trong `USER CODE BEGIN 3`.

Project Tree & Three Flows

Cùng một project, nhưng mỗi sơ đồ trả lời một câu hỏi khác nhau.

Góc nhìnCâu hỏi trả lờiVí dụ thật trong project
Project treeFile nằm ở đâu, và file nào thuộc cùng nhóm?`Core/Inc` chứa interface `.h`; `Core/Src` chứa implementation `.c`; `cmake/stm32cubemx/CMakeLists.txt` đưa các source vào build target.
Runtime / module call flowKhi firmware chạy, hàm và module gọi nhau theo thứ tự nào?`main.c` init peripheral, start PWM và đặt direction; vòng lặp gọi `app_motor_control_update()` → `adc_reader_read_raw()` → map ADC sang Pulse → `motor_pwm_set_pulse()`.
Hardware signal flowTín hiệu điều khiển đi qua các khối phần cứng nào?Potentiometer → `PA0 / ADC1_IN0` → giá trị số được firmware map → `PA8 / TIM1_CH1` PWM → L298N `ENA` → GA37. `PB12/PB13` đi tới `IN1/IN2` để chọn direction.

Đừng trộn ba góc nhìn

Tree không nói hàm nào gọi nhau. Call flow không cho thấy dây nào nối sang L298N. Hardware signal flow không thay thế danh sách file.

Dùng trong portfolio sau này

Muốn cho reviewer thấy cấu trúc source: dùng tree. Muốn giải thích chương trình hoạt động: dùng runtime flow. Muốn giải thích mạch điều khiển motor: dùng hardware signal flow.
